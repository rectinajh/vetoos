# VetoOS 产品化开发清单

> 从「一次性演示」到「用户接进来就能用」。
> 一句话结论：**先做只读影子模式，别碰私钥。** 用户粘一个地址、60 秒内看到自己的报告——
> 这条路零托管、零密钥、零合规风险，而且是唯一能让人"立刻体验到价值"的入口。

---

## 0. 我实测过的前提（决定了哪条路能走）

在写这份清单前，我直接打了主网接口验证，不是假设：

| 验证项 | 结果 | 对产品的意义 |
|---|---|---|
| `clearinghouseState` / `userFills` / `openOrders` / `portfolio` 对**任意地址** | 无需鉴权、无需密钥，直接返回 | 只读产品不需要用户交出任何东西 |
| `userFills` 单地址返回量 | **2000 笔**（最近的），含 `coin, side, dir, px, sz, time, closedPnl, fee, startPosition, oid, cloid` | 足够重建仓位曲线和日内盈亏 → 可以"回放" |
| 活跃账户比例（月成交量前 25 名抽样） | 大量账户**最近 1 小时内**有成交；单账户覆盖 23 个市场 | 影子模式的输入是新鲜且真实的 |
| `startPosition` + `dir` + `closedPnl` | 三者齐全 | 能把历史仓位一步步重建出来，喂给现有引擎 |
| 历史**盘口深度** | 公开接口拿不到 | `BOOK_DEPTH` 这一条规则无法忠实回放 → **必须标记为"当时不可评估"，不许假装**（见 F1.3） |

**结论**：引擎本身（纯函数 + `DecisionInput`）一行不用改就能吃历史数据。缺的只是"谁来喂它"。

## 1. 开工前必须定的三件事（不写代码，但要一天内定）

### 决策 A：托管模型（最重要，选错要重写）

| 方案 | 用户要做什么 | 我们能做什么 | 风险 | 建议 |
|---|---|---|---|---|
| **只读影子** | 粘地址 | 判定、告警、报告 | 无 | ✅ **v1 就做这个** |
| **用户自签执行** | 在钱包里 approve 一个 agent wallet | 用 agent key 下单（不能提币） | 用户输错/被盗用 | ✅ v2 做 |
| **代管私钥** | 交私钥给我们 | 全权 | 法律 + 信任双重自杀 | ❌ 永远不做 |

> 现有代码的关键约束：`packages/adapter-hl/src/index.ts:205` 的 `accountAddress()` 把读操作**硬绑在一个配置地址**上。
> 只读多用户的第一件事就是把它从"配置"改成"入参"。这是 Phase 1 的地基。

### 决策 B：谁付钱、为什么付

三个候选，选一个当主线：
1. **省钱**："上个月有一笔单让 VetoOS 拦下来，能少亏 $X" —— 最容易讲，但难归因；
2. **合规/审计**：收据链 + 选择性披露，卖给需要向 LP 交代的团队 —— 我们已有独家能力；
3. **省事**：托管监控 + 告警 + 策略模板订阅 —— 最标准的 SaaS。

> 建议主线选 2（我们已经做出来了、别人没有），用 1 当获客钩子，3 当续费理由。

### 决策 C：第一批 10 个用户是谁

必须是**能今天就联系上**的具体人：Hyperliquid Discord 里贴成交截图的量化、被爆过仓的 bot 作者。
不是"所有交易者"。

## 2. Phase 1 · 「粘地址就能看到价值」（1–2 周，这是产品本身）

**目标**：新用户在 60 秒内看到一份关于**他自己账户**的报告。

> **进度（已实现）**：F1.1 地址即身份、F1.2 历史回放器、F1.3 诚实处理、F1.4 报告页的 CLI 版本、
> 以及 `packages/replay` + `apps/demo-cli/src/shadow.ts` + `apps/shadowd`（只读托管服务）已落地。
> 实测：任意活跃地址 2000 笔成交，5 次 venue 调用，输出交易画像 + 违规清单 + 归因盈亏 + 5 条明确的"不知道"。
> **还没做**：F1.5 分享链接（托管服务上线后即成立）、按时间分页取更长的历史窗口（venue 单次上限 2000 笔，
> 高频账户只能看到几十分钟）。

- [ ] **F1.1 地址即身份（地基）**
  把 adapter 的账户读接口从 `this.config.accountAddress` 改成显式入参 `getAccountState(network, dex, user)`，
  `getRecentFills(network, user, from)`，`getOpenOrders(user)`。
  **验收**：同一进程能并发查 10 个不同地址且互不串数据。｜~1 天

- [ ] **F1.2 历史回放器（核心）**
  新包 `packages/replay`：输入 `userFills` 序列，输出逐笔 `DecisionInput`。
  - 用 `startPosition` + `dir` 重建每笔成交前后的仓位；
  - 用 `closedPnl` 累加当日已实现盈亏（复用现有的 `refreshDailyPnl` 语义）；
  - 时间窗口（冷却、同向加仓、频率）直接从成交时间轴得出；
  - 逐笔调用现有 `evaluateIntent`，**一行引擎代码都不用改**。
  **验收**：对某个真实地址回放 2000 笔，产出"本会被拦下"的清单，每条带命中规则。｜~3 天

- [ ] **F1.3 历史行情的诚实处理**
  mark 价可以从成交价 + 日线近似；**盘口深度拿不到**。
  → 用 Hydromancer Reservoir（Colosseum 的 Hyperliquid 资源清单里就有，无密钥、requester-pays）补 mark/candles；
  → 补不到的规则，在报告里明确写 `not_evaluable`，而不是给个假结论。
  **验收**：报告里每条结论都能指出它依赖哪些输入、哪些输入缺失。｜~2 天

- [ ] **F1.4 结果页：反事实**
  不讲"我们有多少条规则"，只讲三件事：
  ① 有几笔会被拦下；② 分别撞了哪条规则；③ **如果当时拦住，按后续价格算你少亏/少赚多少**（两个数都给，不许只报好看的）。
  **验收**：一个不懂永续合约的人也能看懂这页。｜~2 天

- [ ] **F1.5 分享链接**
  报告生成一个只读链接（含地址 + 时间范围 + 收据根），可发群里。
  这既是增长回路，也顺手展示了"可验证"——别人能独立复算这份报告。｜~1 天

> **Phase 1 完成的标志**：把一个陌生人的地址粘进去，他自己会截图发出去。

## 3. Phase 2 · 从「看」到「管」（留存，2–4 周）

- [ ] **F2.1 用户与数据层**
  现在状态是 `broker-state.json` + JSONL + 单写锁（`brokerd.lock`）。多用户必须换成：
  Postgres（用户、策略、收据索引）+ 对象存储（归档输入，现在是一堆小文件）。
  **每用户一条独立收据链**，不要混在一条链里（否则没法选择性披露）。｜~1 周

- [ ] **F2.2 策略编辑器**
  `configs/policy.demo.json` 的字段做成表单 + 三档模板（conservative/degen/fund 已有）。
  每次保存 = 新 `policySemanticHash` + 一条 `policy_change` 收据。
  ⚠️ 注意：`policy_change` 目前只是 `AuditEventType` 里声明过的类型，**没有写入路径**——
  需要补一个 `recordPolicyChange()`（含旧/新语义哈希 + 人类签名 + 生效 seq）才算闭环。｜~4 天

- [ ] **F2.3 实时监控 + 告警**
  现在没有任何 WebSocket（track 资源里 `WebSocket API` 那条明确要求"显式重连与心跳"）。
  接 `userFills` / `webData2` 订阅，规则命中 → Telegram/Discord/邮件。
  **这是留存的关键**：用户不登录也会被提醒。｜~1 周

- [ ] **F2.4 持续影子模式**
  用户把自己的策略/agent 的意图 POST 进来，我们只判定不执行，返回 allow/deny + 收据。
  这一步零风险，却能让用户先跑两周再决定要不要给执行权。｜~3 天

> **Phase 2 完成的标志**：用户每周主动回来 3 次以上，且开始抱怨"为什么某条规则没拦住"。

## 4. Phase 3 · 从「管」到「执行」（收费，1–2 月）

- [ ] **F3.1 agent wallet 授权流**
  用 Hyperliquid 的 `approveAgent`：**用户在自己钱包里签**，agent 私钥由我们生成但只能交易、不能提币。
  这是全流程唯一需要用户"交出东西"的一步，必须做成三屏以内、可随时撤销。｜~1 周
- [ ] **F3.2 多租户执行隔离**
  每用户独立进程/容器 + 独立密钥 + 独立额度；一个用户被攻破不能影响别人。
  现有 `RiskBroker` 是单例，需要按账户实例化。｜~2 周
- [ ] **F3.3 最终确认（可选档）**
  超过阈值的大单要求用户在手机上点一次确认（我们已有 EIP-191 绑定状态的签名流程，扩展即可）。｜~4 天
- [ ] **F3.4 builder code 收入**
  adapter 已有 `builderAddress` / `builderFeeTenthsBps` 占位，主网接上即可计费。｜~3 天

> **完成的标志**：第一笔**用户授权**的真实成交，并且它的收据能被用户自己 `pnpm verify` 验过。

---

## 5. Phase 4 · 基础设施（与 Phase 3 并行）

- [ ] 部署：Dockerfile + compose（现在没有），托管环境、TLS、域名
- [ ] 密钥管理：所有私钥进 KMS/Secrets Manager，禁止再出现 `.env` 明文（现在 `HL_PRIVATE_KEY` 是明文）
- [ ] 可观测性：结构化日志 + metrics（现在两者都没有）+ 状态页 + 告警
- [ ] 配额与限流：每用户 API 配额；主网 info 接口我们已经实测会 429，必须做全局限流池
- [ ] 备份与恢复：收据链和归档输入是**用户资产的证据**，丢了就没法自证
- [ ] 锚定批量化：现在是单机 `pnpm anchor`；多用户要批量 Merkle 根 + 定期上链

---

## 6. 明确不做（写进 README，防止自己手痒）

- ❌ 代管用户私钥（一票否决）
- ❌ 跟单/社交交易（合规性质变了，且和"规则胜过模型"的定位冲突）
- ❌ 自营策略/资金池（角色冲突：既当裁判又当选手，我们的卖点就没了）
- ❌ 在只读模式里给"投资建议"口吻的结论（说"这笔会被规则拦下"，不说"你不该买"）

---

## 7. 如果只有一周：只做这五件事

1. F1.1 地址即身份（1 天）
2. F1.2 历史回放器，先支持"名义额 / 杠杆 / 日内亏损 / 同向加仓 / 频率"这 5 条**只依赖账户与时间**的规则（3 天）
3. F1.3 在报告里如实标注 `BOOK_DEPTH` 不可评估（半天）
4. F1.4 结果页 + 反事实数字（2 天）
5. F1.5 分享链接（半天）

> 一周后你能拿到的不是"一个平台"，而是**一条能发出去的链接**。
> 拿它去换 10 个真实用户的反馈，再决定 Phase 2 做什么——这比先建用户体系再想价值主张快 10 倍。
